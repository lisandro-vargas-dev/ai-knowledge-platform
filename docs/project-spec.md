# AI Knowledge Platform — Project Specification

## Document status and execution scope

This document defines the product and its incremental development milestones. It is not a claim that any feature is already implemented.

The initial development target is Milestone 1. Reading or installing this specification does not authorize implementation by itself: follow the current user request and stop when its authorized scope is complete.

Language and execution conventions are defined in `.agents/rules/project-policy.md`. Repository documents remain in English; user-facing explanations are in Spanish by default.

This specification preserves the product, stack, and phase order from the supplied Project 01 specification and the preceding development brief. The initial UI arrangement, folder layout, and exact health-response JSON remain implementation proposals, not requirements from the original product specification. No personal background or unrelated product context is required.

## 1. Product

Build an AI knowledge platform where a user can:

1. Create or use a workspace.
2. Upload documents to the workspace.
3. Process and index those documents.
4. Ask questions about the uploaded knowledge.
5. Retrieve relevant information.
6. Receive an answer generated by an LLM.
7. Inspect the sources used to produce the answer.

The eventual AI architecture uses Retrieval-Augmented Generation (RAG): retrieve relevant content and generate answers grounded in that content.

The application must be reproducible, tested, maintainable, and genuinely usable. A visual mockup or an isolated LLM API call is not the completed product.

Do not describe planned capabilities as implemented capabilities.

## 2. Target architecture

### Frontend

- React and TypeScript.
- HTTP communication with the backend.
- Streaming when its milestone is reached.

### Backend

- Python and FastAPI.
- Pydantic for validation and schemas where appropriate.
- Environment-based configuration.

### Data and infrastructure

- PostgreSQL for persistence.
- pgvector for embeddings and vector search.
- Redis when a concrete need justifies it.
- Docker and Docker Compose in their milestone, not on day one.

### AI

- OpenAI API as the planned provider.
- Model selection through configuration rather than hard-coded model names.
- Embeddings, retrieval, RAG, and source attribution.
- Error handling and appropriate measurement of latency, tokens, and cost.

### Quality and delivery

- pytest for backend testing.
- Frontend tests when a frontend exists.
- Git and GitHub.
- GitHub Actions in the automation milestone.
- Logging, observability, and actual measurements.

Do not replace the stack or add services without explaining the need and obtaining approval.

## 3. Proposed interface

At the frontend milestone, propose a simple interface with:

- Workspace selection.
- A document area with upload controls and processing status.
- A question-and-answer area.
- Sources associated with each answer.
- Loading, error, and empty states.

This is an initial layout proposal, not a finalized visual design. Features should become available as their supporting backend functionality is implemented.

Do not build misleading screens that imply document retrieval already exists.

## 4. Development milestones

### Milestone 1 — Python and FastAPI

Initial project structure, dependency management, minimal configuration, `GET /health`, appropriate error handling, and basic tests.

### Milestone 2 — LLM API integration

Connect OpenAI API through the backend. Configure credentials and the model through the environment. Handle requests, responses, errors, appropriate retries, and usage limits. Add structured outputs where useful. Confirm credentials and cost controls before real external calls.

### Milestone 3 — React and TypeScript integration

Connect the frontend to the backend. Implement a chat interface with loading and error states. Document-grounded conversation comes after retrieval is implemented.

### Milestone 4 — PostgreSQL

Add database configuration, migrations, and persistence. Design users, workspaces, and documents as needed for this phase.

### Milestone 5 — Document ingestion

Agree on the initially supported document formats. Implement extraction, cleaning, chunking, and metadata.

### Milestone 6 — Embeddings and vector search

Generate embeddings, store them in PostgreSQL with pgvector, and retrieve relevant chunks. Define chunking, similarity, and metadata-filtering strategies.

### Milestone 7 — RAG

Implement the pipeline:

`Question -> embedding -> retrieval -> context construction -> LLM -> answer with sources`

Sources must correspond to content actually retrieved for the answer.

### Milestone 8 — Streaming

Display responses progressively using a suitable mechanism. Evaluate SSE for this flow.

### Milestone 9 — Evaluation

Create a small dataset of questions, expected answers, and relevant sources. Measure retrieval quality, answer correctness, citation correctness, latency, token usage, and cost where practical. Do not claim unmeasured results.

### Milestone 10 — Docker

Prepare containers and Docker Compose for the implemented components. Do not add unused components merely to complete an architecture diagram.

### Milestone 11 — CI/CD

Automate tests, linting, and build verification with GitHub Actions where appropriate.

### Milestone 12 — Observability and performance

Introduce structured logging, useful error information, and latency measurements. Add tracing or caching when justified by actual needs.

### Milestone 13 — Deployment

Select a practical environment and deploy securely. Agree on services, credentials, and possible costs beforehand.

### Milestone 14 — Repository quality

Complete the README, architecture diagram, setup instructions, API documentation, demo, tests, evaluation methodology, measured results, technical decisions, trade-offs, limitations, and future improvements.

Do not advance automatically. Resolve details that remain unspecified when their milestone is reached instead of inventing requirements in advance.

## 5. Milestone 1 implementation scope

When the user explicitly requests implementation of Milestone 1, inspect before editing:

- Confirm and show the working directory.
- Inspect existing files and Git status.
- Check available Python and Git versions.
- Preserve existing code and unrelated changes.
- Briefly state the plan and the expected file changes.

Then implement only the following:

1. Initialize a local Git repository if one does not exist. Do not create or publish a remote repository without authorization.
2. Create a small backend structure without unnecessary layers or abstractions.
3. Prepare a local virtual environment and reproducible dependency management. Do not install Python packages globally.
4. Create the FastAPI application.
5. Implement `GET /health`.
6. Use the proposed initial contract: HTTP 200 with exactly `{"status":"ok"}`.
7. Use a Pydantic response schema if it keeps the implementation clear and simple.
8. Add only genuinely useful environment configuration. Include `.env.example` when appropriate, without sensitive values.
9. Add at least one automated test that verifies both the HTTP status and the JSON response from `/health`.
10. Add `.gitignore` entries for virtual environments, actual `.env` files, caches, and generated files. Keep `.env.example` trackable if present.
11. Write an English README with exact Windows PowerShell commands for installing dependencies, starting the backend, and running tests.
12. Run the tests and address failures within the implementation scope.
13. Verify actual server startup and a real local HTTP request to `/health`, separately from the automated test.
14. Show changes and stop before committing.

On Windows, commands may invoke the virtual environment's `python.exe` directly. Do not change global PowerShell execution policy to activate the environment.

Do not implement frontend, LLM calls, authentication, documents, databases, embeddings, RAG, Redis, Docker, or deployment in this milestone.

This milestone makes no LLM provider calls and requires no API key.
